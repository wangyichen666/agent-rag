## Q1：换模型 provider 要改什么？Formatter 解决什么问题？

### 【模范回答】

先说结论：换 provider 只换 model 类 + credential，**业务代码一行不改**。这是 Formatter 这层抽象的功劳。

问题背景是：不同 provider 的 API 格式天差地别。同样一条消息，OpenAI 是 `content: [{type:"text", text:"..."}]`，Claude 的 tool 格式又是另一套，Gemini 用 `parts: [...]`，DashScope 又有自己的 extra_body 字段（比如 thinking、top_k 要塞进 extra_body）。如果业务代码直接拼各 provider 的格式，换一个模型就要改一片代码，而且容易出错。

Formatter 是中间的**翻译层**：业务代码永远用 agentscope 统一的 `Msg`/`ContentBlock`，Formatter 负责把它们翻译成目标 provider 的原生格式。每个 provider 内置了对应的 Formatter（DashScopeChatModel 默认就用 DashScopeChatFormatter），你一般不用手动设。所以换 provider 的全部工作就是：把 `DashScopeChatModel(credential=DashScopeCredential(...))` 换成 `AnthropicChatModel(credential=AnthropicCredential(...))`，Agent 那边 `model=model` 一行不变，业务逻辑全不动。

有个细节值得讲——每个 provider 其实有**两个** Formatter：`XxxChatFormatter`（单 Agent 对话）和 `XxxMultiAgentFormatter`（多 Agent 场景）。区别在于多 Agent 时，多个 Agent 的来回发言不能直接用 role 区分（角色会乱），所以 MultiAgent Formatter 会把历史消息**折叠**，多个 Agent 的回合包成一个 `<history>` 塞进 user 消息，让 API 看到的是干净的 user/assistant 交替。多 Agent 场景用错 Formatter 会因角色混乱报错，这是个坑。

另外 Formatter 还处理 provider 的能力差异——比如 ThinkingBlock（思考块），OpenAI 的 Formatter 会丢弃它（API 不接受），Anthropic 保留但要求带 signature。这些 provider 坑都被 Formatter 封掉了。

> **要点速记**：① 换 provider 只换 model 类+credential，业务代码不改；② Formatter 是翻译层，统一 Msg→各 provider 原生格式；③ 每 provider 两个 Formatter：Chat(单Agent)/MultiAgent(多Agent折叠history防角色乱)；④ Formatter 封掉 provider 能力差异(如 ThinkingBlock 跨provider 丢弃/保留)。
>
> **源码佐证**：9 个 provider Formatter（`formatter/`：_anthropic/_dashscope/_gemini/_openai 等）+ 基类 `FormatterBase`；DashScope 默认挂 `DashScopeChatFormatter`（`model/_dashscope/_model.py:151`）。
>
> **压轴一句话**：Formatter 是统一 Msg 到各 provider 原生格式的翻译层，换 provider 只换 model 类业务不动；每 provider 有 Chat/MultiAgent 两个 Formatter，多 Agent 必须用 MultiAgent 版否则角色乱。

## Q2：怎么让模型返回结构化数据？为什么要用它？

### 【模范回答】

默认情况下模型返回的是自由文本，你想要结构化数据（比如抽取实体、分类、生成计划）就得自己解析文本——写正则、容错，很脆弱，模型换个说法你就解析不出来。

agentscope 提供 `model.generate_structured_output(messages, structured_model=Pydantic类)` 直接拿强类型结果。你传一个 Pydantic model（或 JSON Schema dict）进去，返回的 `StructuredResponse.content` 就是符合 schema 的 dict，你能直接 `MyModel(**res.content)` 变成强类型对象。

它的实现原理挺巧——**用工具调用模拟结构化输出**。框架把你传的 schema 包装成一个名为 `generate_structured_output` 的「工具」，用 `tool_choice` 强制模型必须调用这个工具，模型一调用，它的参数 JSON 就是符合 schema 的结构化结果。换句话说，它复用了 Function Calling 的机制来强制结构化。默认实现是这样（`_call_api_with_structured_output`）；如果某个 provider 原生支持结构化输出，可以 override 走原生更高效。

还有个延伸用法——**上下文压缩也用了它**。前面 W07 讲过，`_compress_context_impl` 要让模型生成摘要，它不是让模型自由写，而是传 `SummarySchema`（五字段：task_overview/current_state/important_discoveries/next_steps/context_to_preserve）调 `generate_structured_output`，强制模型按这五段输出——这样压缩出来的不是一段散文，而是结构化的「任务进度档案」。同一个机制，两个用途。

**什么时候用结构化输出**：要确定性结构的场景——信息抽取（姓名/年龄/爱好）、分类（标签枚举）、计划生成（步骤数组）、配置生成。凡是「我要把模型输出喂给后续代码处理」的，都该用结构化而不是解析自由文本。代价是稍微约束了模型自由度，但对工程确定性来说值得。

> **要点速记**：① generate_structured_output 传 Pydantic 拿强类型结果，告别正则解析；② 原理：把 schema 包成工具用 tool_choice 强制模型调用，复用 Function Calling；③ 上下文压缩也用它（SummarySchema 五字段强制结构化）；④ 用于要确定性结构的场景：抽取/分类/计划/配置。
>
> **源码佐证**：`generate_structured_output`（`model/_base.py:438`）；默认实现 `_call_api_with_structured_output`（:503）；压缩复用（`agent/_agent.py:465`）；DashScope 开 thinking 时降级 tool_choice 的 provider 适配（`model/_dashscope/_model.py:534`）。
>
> **压轴一句话**：传个 Pydantic 进 generate_structured_output 拿强类型结果，原理是用 tool_choice 强制模型调用"schema工具"，正则解析自由文本的脆弱事儿就免了——抽取/分类/计划/压缩都用它。

## Q3：怎么把 Agent 流式输出变成工业级 SSE 服务？

### 【模范回答】

分两层讲——框架层和服务化层。

**为什么要流式**：生成式模型是逐 token 吐的，如果等整句生成完再返回，用户要干等几秒到几十秒才看到首字；流式边生成边推，首字延迟降到几百毫秒。技术上 agent 的 `reply_stream` 返回 `AsyncGenerator[AgentEvent]`，每个事件是一帧。

**但 reply_stream 不能直接裸暴露给前端**——这是新手常犯的错。框架事件很「碎」：一堆 `TEXT_BLOCK_DELTA` 增量，没有序号、没有完成态、断线就丢。工业级要解决三个问题：消息要有序可终结、断线要能恢复、请求生命周期要可治理。所以中间要加两层。

第一层 **Envelope 状态机**。它是个翻译器：吃进碎的 AgentEvent，吐出标准的 SSE 消息（`data: {seq, type, data}\n\n`）。内部维护状态字典——比如 `{block_id: 已累积文本}`，delta 来了就累加，结束时 finalize。每条消息打 seq 序号，客户端断线重连后能按 seq 续传，不丢消息。这层解决「碎→标准 + 可恢复」。

第二层 **Runtime 阶段化**。把一次 HTTP 请求拆成有序阶段（pre_dispatch 鉴权、pre_agent_build 组装 Agent、pre_execute 限流、execute 执行、post_response 审计……），每阶段是可插拔 hook 点。新功能（加限流、加审计）= 注册一个 hook，不改主流程；且每阶段用 shield 保护，一个插件挂了不拖崩整个请求。这层解决「生命周期可治理 + 可扩展」。还要加心跳，周期性发 keepalive 防 SSE 长连接被代理超时断开。

最终一个请求进来：鉴权（pre_dispatch）→ 组装（pre_agent_build）→ 限流（pre_execute）→ 执行 Agent 吃事件流 → 经 Envelope 翻译成标准 SSE 推给客户端 → 审计（post_response）。这就是 agentscope `app/_router/_session.py` 的 SSE 端点 + QwenPaw Runtime/Envelope 的完整工业实现。直接 `StreamingResponse(reply_stream)` 是 demo 级，加了 Envelope+Runtime 才是生产级。

> **要点速记**：① 流式降首字延迟（逐token推），reply_stream 是 AsyncGenerator；② 不能裸暴露——事件碎/无序号/断线丢；③ 加 Envelope 状态机：碎事件→带seq标准SSE，维护累积状态，支持断线续传；④ 加 Runtime 阶段化：鉴权/组装/限流/执行/审计各阶段 hook，可扩展可治理；⑤ 加心跳防超时。裸 StreamingResponse 是 demo，Envelope+Runtime 才是生产。
>
> **源码佐证**：SSE 端点 `app/_router/_session.py`；产品级 Envelope（`runtime/envelope.py:27`，`translate_event:138`，`_text_blocks` 状态:180，seq `_next_seq:80`）；Runtime 阶段（`runtime/runtime.py:49`，8阶段 + per-hook shield `:239`）。
>
> **压轴一句话**：reply_stream 是原料不能裸暴露，要加 Envelope（碎事件→带序号可恢复的标准SSE）+ Runtime（阶段化hook可治理可扩展）+ 心跳，三层齐了才是生产级 SSE——直接 StreamingResponse 只是 demo。
