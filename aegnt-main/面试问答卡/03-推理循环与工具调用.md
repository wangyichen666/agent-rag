> 覆盖：W3 / W4。对应 JD：Agent Loop 智能循环、Function Calling、任务自主迭代/中断恢复/异常重试。

## Q1：Function Calling 的本质是什么？模型会真的执行工具吗？

### 【模范回答】

这里有个常见的误解，很多人以为「模型调用了工具」就是模型自己去执行了——**不是的。模型本身不执行任何东西，它只决策**。

Function Calling 的本质是：你给模型一份「工具说明书」（用 JSON Schema 描述每个工具的名字、用途、参数），模型在回答问题时，可以选择输出一个**结构化的工具调用请求**——「我想调用 get_weather 这个工具，参数是 `{city: "杭州"}`」。注意，这只是一段结构化的输出，一个意图声明。真正去执行 `get_weather("杭州")` 的，是**你的代码**。你拿到模型的这个请求，调真正的函数，拿到结果（"28度晴"），然后把这个结果作为一条 `tool` 角色的消息塞回对话历史，再让模型看一眼。模型看到「我刚才要查杭州天气，结果是 28 度晴」，于是基于这个结果继续推理——要么再调下一个工具，要么给出最终答案。

所以整个循环是：**模型决策 → 你的代码执行 → 结果回填 → 模型再决策**。模型是「大脑」负责判断该用什么工具、传什么参数；你的代码是「手脚」负责真正执行。这个分工非常重要，因为意味着：工具的安全性、超时、重试、权限，全在你的代码掌控里，模型没法绕过——这就给了工程治理的抓手（W10 讲的沙箱、审计、权限都建立在这个基础上）。

实现上，工具的 JSON Schema 既可以手写（像我 W3 手写 ReAct 就手写了 TOOLS 字典），也可以让框架从 Python 函数的**签名 + docstring 自动生成**——agentscope 的 `FunctionTool` 就是这么做的，你写个带类型注解和 docstring 的函数，它自动抽出参数 schema，比手写稳。模型返回的工具调用，框架统一用 `Toolkit.call_tool` 执行，结果归一化成 `ToolResultBlock` 回填。

> **要点速记**：① 模型不执行，只输出结构化「我想调X」的意图；② 真正执行是你的代码；③ 循环=模型决策→代码执行→结果回填tool消息→模型再决策；④ 工具安全性/超时/重试/权限全在代码侧可控（治理抓手）；⑤ schema 可手写或从函数签名+docstring 自动生成（FunctionTool）。
>
> **源码佐证**：`Toolkit.call_tool`（`tool/_toolkit.py:225`）统一执行入口；`FunctionTool`（`tool/_adapters.py:31`）自动抽 schema；`ToolResultBlock`（`message/_block.py:167`）回填结果。
>
> **压轴一句话**：模型是大脑只决策不执行，工具调用是个意图声明，真正跑的是你的代码——结果以 tool 消息回填让模型再看一眼，安全/超时/权限全在代码侧可控。

## Q2：手写 ReAct 循环怎么判断结束？多个工具调用怎么执行？框架比你手写多了什么？

### 【模范回答】

先说**结束判断**。这个最直接：看模型返回的 `tool_calls` 字段。如果它**为空**，说明模型这次不再要调工具了——那它输出的就是最终答案，循环结束；如果**非空**，说明模型还想调工具，那就执行这些工具、把结果回填，继续下一轮。但光这样不够，得加个 `max_iters` 兜底——万一模型陷入死循环（反复调同一工具不收敛），没有上限就永远停不下来。所以终止条件是两条：模型不再要工具（正常结束），或达到最大迭代数（强制停）。agentscope 默认 `max_iters=20`。

**多个工具调用怎么执行**——这有个优化点。模型一轮可能同时要调好几个工具。如果都串行执行，等一个跑完再跑下一个，慢。框架的做法是按工具的 `is_concurrency_safe` 属性分两批：标记了「并发安全」的工具（比如只读查询）放 concurrent 批，用 `asyncio` 并发跑；有副作用、不安全的（比如写文件）放 sequential 批，串行跑。这样安全的前提下尽量并发，省时间。W3 我手写的版本是纯串行，框架这块是实打实的工程优化。

**框架比手写多了什么**——这正好是我 W3 手写 ReAct 后对照框架总结的，也是面试讲项目有深度的地方。我手写的 50 行轮子，逻辑上对应框架的 `_reply_impl`：我的「tool_calls 为空就结束」对应框架的 `_check_next_action`，我的「调模型」对应 `_reasoning`，我的「执行+回填」对应 `_execute_sequential/concurrent_tool_calls`。但框架额外做了五件我手写时没做的事：

1. **并发分批**（上面说的 sequential/concurrent）；
2. **上下文压缩**：每轮推理前检查 token，超 80% 就压成结构化摘要，防上下文爆炸——我手写时就撞上了这个坑，历史越跑越长；
3. **事件流**：每个阶段 yield 事件，UI 能实时渲染思考、工具调用、文字；
4. **人在回路/中断**：`RequireUserConfirmEvent` 让危险操作能暂停等人确认，`UserInterruptEvent` 能中断恢复；
5. **异常重试与降级**：`ModelConfig.max_retries` 重试可重试异常，主模型挂了切 `fallback_model` 降级。

所以「手写 50 行」和「用框架」的差距，就是这五层工程。我面试时讲项目就是：「我先手写了个 50 行 ReAct，撞上上下文爆炸、工具结果过长、死循环三个坑，然后看框架怎么解的——压缩、截断、stop gate，这样理解框架就不是背 API 而是知其所以然。」

> **要点速记**：① 结束判断=tool_calls 为空(正常) 或 达 max_iters(强制)；② 多工具按 is_concurrency_safe 分 sequential/concurrent 两批；③ 框架比手写多五层：并发分批/上下文压缩/事件流/人在回路中断/重试降级；④ 手写轮子对应 _reply_impl 的 check_next_action+reasoning+execute。
>
> **源码佐证**：`_reply_impl`（`agent/_agent.py:664`）；`_check_next_action`（:2542）；`_reasoning`（:916）；`_execute_sequential_tool_calls`（:1375）/`_execute_concurrent_tool_calls`（:1425）；每轮压缩调用点 `:759`；`ReActConfig.max_iters`（`_config.py:126`）；`ModelConfig.max_retries/fallback_model`（`:164`）。
>
> **压轴一句话**：tool_calls 空就结束、max_iters 兜底，多工具按并发安全分批执行；框架比手写多了并发/压缩/事件流/中断恢复/重试降级五层——手写撞坑、框架填坑，这才叫懂框架。

## Q3：Agent 循环怎么中断、怎么恢复、怎么处理异常？

### 【模范回答】

这三件事生产环境必须解决，框架都有机制。

**中断**。两种主动中断。一是**人在回路**：当 Agent 要执行一个有风险的操作（比如删文件、跑 shell 命令），它不直接执行，而是 yield 一个 `RequireUserConfirmEvent` 暂停下来，等用户在前端点「允许/拒绝」。用户的选择通过 `UserConfirmResultEvent` 喂回去，Agent 据此继续或放弃。二是**用户主动打断**：用户等不及或想改方向，发一个 `UserInterruptEvent`，Agent 会把所有 pending 的工具调用标记为 INTERRUPTED，干净地结束这一轮。

**恢复**。关键在于**状态持久化**。Agent 的状态（context 消息历史、当前迭代号、工具调用状态）通过 `state_dict()` 可以序列化存起来，需要时 `load_state_dict()` 恢复。这样即使进程挂了、连接断了，下次能从上次的状态接着跑，不丢上下文。在产品层，QwenPaw 的 Runtime 把一次请求拆成 8 个阶段，每个阶段是粒度更细的 checkpoint——断连后能按阶段 resume，比「全跑完才存」粒度细得多。SSE 层面，Envelope 给每条消息打 seq 号，客户端断线重连后能按序号续传，不丢消息。

**异常处理**分几个层面。模型调用层：`max_retries` 对可重试异常（网络错、限流、服务端 5xx）自动重试，全失败还有 `fallback_model` 降级到备用模型——主模型挂了不至于整个 Agent 停摆。工具执行层：工具抛异常不会被框架直接 crash，而是转成 `ToolResultState.ERROR` 的工具结果回填给 Agent，让 Agent 自己看到「这个工具失败了」并决定怎么处理（换个参数重试、换工具、或告诉用户）——这叫「自我纠偏」。如果是开发者代码 bug（`DeveloperOrientedException`），框架会重新抛出让开发者修，而不是吞掉。循环层：`max_iters` 兜底死循环，超出 yield `ExceedMaxItersEvent` 干净结束，不会无限转。

这套「中断有事件、恢复有持久化、模型有重试降级、工具有自我纠偏、循环有兜底」，就是生产级 Agent 和玩具 demo 的区别。每个点都对应 JD 里「任务自主迭代、中断恢复、异常重试、主动思考纠偏」。

> **要点速记**：① 中断两种——人在回路(RequireUserConfirm)和用户打断(UserInterrupt)；② 恢复靠 state_dict 持久化 + Runtime 阶段 checkpoint + SSE seq 续传；③ 模型异常=max_retries 重试 + fallback_model 降级；④ 工具异常=转 ERROR 结果回填让 Agent 自我纠偏(不 crash)；⑤ 循环兜底=max_iters + ExceedMaxItersEvent。
>
> **源码佐证**：`UserConfirmResultEvent`/`UserInterruptEvent`（`event/_event.py:55-60`）；`state_dict`/`load_state_dict`（QwenPaw `agents/react_agent.py:174/187`）；`ModelConfig.max_retries/fallback_model`（`agent/_config.py:164`）；`ToolResultState.ERROR/INTERRUPTED`（`message/_block.py:157`）；`ExceedMaxItersEvent`（`event/_event.py:53`）。
>
> **压轴一句话**：中断靠确认/打断事件，恢复靠状态持久化+阶段checkpoint+seq续传，模型靠重试+降级，工具异常转结果让Agent自我纠偏、循环 max_iters 兜底——这套是生产级和玩具 demo 的分水岭。
