## Q1：agentscope 2.0 的消息结构为什么不是字符串？Msg、ContentBlock、Event 三层是什么关系？

### 【模范回答】

这是 2.0 相对 1.0 一个很关键的演化。1.0 时代消息基本就是 `{role, content: 一段字符串}`，这在纯对话场景够用。但现代 Agent 要处理的东西远不止文本——一条助手消息可能同时包含：模型的**思考过程**（reasoning/思考块）、**纯文本回复**、**它要调用的工具请求**、**工具执行的结果**，甚至图片音频这类**多模态数据**，还有给模型的**隐式提示**。这些东西塞不进一个字符串，硬塞就要自己解析，非常脆弱。

所以 2.0 采用了「**content 是 ContentBlock 列表**」的设计。一条 `Msg` 的 `content` 字段是 `list[ContentBlock]`，每个 block 是一种内容单元：`TextBlock`（文本）、`ThinkingBlock`（思考）、`ToolCallBlock`（工具调用请求）、`ToolResultBlock`（工具结果）、`DataBlock`（多模态）、`HintBlock`（给模型的隐式提示，不回显给用户）。一条 assistant 消息可以是 `[TextBlock, ToolCallBlock]` 的组合——模型一边说话一边顺手调个工具，这在 1.0 的字符串里表达不了。这个设计和 Claude、OpenAI 的 content-parts 思路是一致的，是当下的主流。

至于为什么还要有 **Event** 这一层——因为流式。模型是逐 token 吐出来的，Agent 的整个生命周期是一条**事件流**：`REPLY_START` → `MODEL_CALL_START/END` → `TEXT_BLOCK_START/DELTA/END`（文字逐块）→ `TOOL_CALL_*` → `REPLY_END`。每个阶段发对应事件，下游（UI、日志、监控）按需订阅。

这三层的关系是：**`Msg` 是对外消息单元（一条完整消息），`ContentBlock` 是内容单元（消息里的一种内容），`Event` 是流式传输中的增量信号（生命周期的一帧）**。它们不是平级替代，而是不同抽象层：流式时用 Event 一帧帧推，最终用 `Msg.append_event()` 把碎事件拼装成完整的 Msg。解耦是核心价值——Agent 只管发事件，不关心谁在听；前端只管订阅事件，不关心 Agent 内部怎么跑。

> **要点速记**：① 字符串表达不了「边说话边调工具+思考+多模态」，故用 block 列表；② Msg=消息单元 / ContentBlock=内容单元 / Event=流式增量帧，三层不同抽象；③ assistant 消息可同时含 TextBlock+ToolCallBlock；④ 流式用 Event 推、append_event 拼成 Msg；⑤ Agent 发事件→下游订阅，解耦。
>
> **源码佐证**：`Msg`（`message/_base.py:66`）；六种 Block（`message/_block.py`：TextBlock:11/ThinkingBlock:22/ToolCallBlock:114/ToolResultBlock:167/DataBlock:67/HintBlock:81）；EventType 全枚举（`event/_event.py:24-62`）；`UserMsg/AssistantMsg/SystemMsg` 是工厂函数（`:476/524/573`）。
>
> **压轴一句话**：消息不是字符串而是 ContentBlock 列表（一条消息可同时含文字+工具调用），Msg/Block/Event 三层各司其职，流式用 Event 推、最终拼成 Msg，Agent 发事件下游订阅全程解耦。

## Q2：agentscope 2.0 的多 Agent 怎么编排？为什么没有 Pipeline？

### 【模范回答】

这是 2.0 迁移最反直觉的一点，也是面试的高频考点。1.0 时代做多 Agent 是**代码级编排**：你在 Python 里写 `SequentialPipeline([agent1, agent2])`，或者用 `MsgHub` 共享消息，编排逻辑写死在代码里。2.0 把这一整套**全删了**——`Pipeline`、`Pipe`、`MsgHub`、`SequentialPipeline` 在 2.0 源码里都不存在了。

那 2.0 怎么编排多 Agent？答案是**服务级编排**：一个 Leader Agent 通过**工具调用**来管理团队。具体说，框架在服务层提供了一组「团队工具」——`TeamCreate`（建团队，当前会话成为 Leader）、`AgentCreate`（spawn 一个 Worker，给它指定 prompt 和权限）、`TeamSay`（Leader 和 Worker 之间单播或广播通信）、`TeamDelete`（解散）。Leader 调用这些工具，就像它调用 Bash 或搜索工具一样——「管理一个 Worker」对 Leader 来说本质上就是一个 tool call。

Worker 之间、Worker 和 Leader 之间的消息走一条**消息总线 MessageBus**（有内存版和 Redis 版）。Worker 是**独立的 session**，有自己的上下文，天然隔离、可并发。换 Redis 版 MessageBus 就能多 worker 进程横向扩展、支持多租户。

**为什么要这么改？** 核心动机是「编排由模型动态决策，而非代码静态写死」。代码 pipeline 是固定的——A 完了一定给 B，但真实任务里「资料不够要不要再查、稿子太差要不要再审一轮」是动态的，应该由模型根据中间结果判断，而不是写死 if-else。用工具调用的方式，模型可以自主决定「现在 spawn 一个 Worker」「现在让 Worker 重做」，灵活得多。而且这套设计天然支持并发（多 Worker 独立 session）、可扩展（Redis 总线）、可多租户。

我自己的毕业项目就用了这套：Leader 拆任务，用 AgentCreate 拉 Researcher/Writer/Reviewer，用 TeamSay 派活收活。如果用 1.0，我就得 `pipeline([researcher, writer, reviewer])` 写死顺序，没法应对「Review 评分低就让 Writer 再改」这种动态分支。

所以面试时遇到「找 Pipeline 找不到」不是我看漏了，是 2.0 的设计——**多 Agent 协作 = Leader 用工具调度 + 消息总线**，编排藏在服务层工具里，不在框架核心类里。

> **要点速记**：① 2.0 删了 Pipeline/Pipe/MsgHub，没有代码级编排；② 改成服务级编排——Leader 用 TeamCreate/AgentCreate/TeamSay 工具调度；③ 消息走 MessageBus（内存/Redis），Worker 独立 session 隔离并发；④ 动机：编排由模型动态决策非代码写死，支持并发/扩展/多租户；⑤ 别找 Pipeline，编排藏在服务层工具里。
>
> **源码佐证**：团队工具 `app/_tool/_team_create.py`/`_agent_create.py`/`_team_say.py`/`_team_delete.py`；MessageBus `app/message_bus/_in_memory_message_bus.py`/`_redis_message_bus.py`；会话管理 `app/_service/_session.py`。
>
> **压轴一句话**：2.0 没有 Pipeline——多 Agent 靠 Leader 用 Team 工具动态调度 + MessageBus 收发，编排由模型决策而非代码写死，换 Redis 就能扩展多租户。

## Q3：怎么把单进程 Agent 变成可并发、可扩展的生产服务？

### 【模范回答】

Agent 的 `reply_stream` 本身是个异步生成器，但浏览器、curl 拿不到生成器，所以要包成 HTTP 服务。生产化分几步。

第一步，**把 reply_stream 包成 SSE 长连接端点**。一个 `GET /sessions/{sid}/stream` 长连接，客户端连上来，服务端把 Agent 的事件一条条用 SSE 格式（`data: {...}\n\n`）推过去，加心跳保活防代理超时断开。这里有个**工业化的关键中间层**——不能直接裸暴露 reply_stream，因为框架事件很「碎」（一堆 delta），前端要的是有序、可恢复的标准消息。所以要加一个 **Envelope 状态机**做翻译：吃进碎事件，吐出带序号（seq）、可终结（finalize）的标准 SSE 消息，还支持断线重连续传。再往上是 **Runtime**，把一次请求拆成有序阶段（pre_dispatch 鉴权、pre_agent_build 组装、pre_execute 限流、post_response 审计……），每个阶段是可插拔 hook 点，新功能挂 hook 不改主流程。

第二步，**会话状态管理**。多用户多会话不能各自存在内存里就完事，要用一个 `SessionService` 管理会话生命周期（创建、调度、暂停、恢复、销毁），状态机化，支持 cancel/delete 和团队级联清理。存储放 Redis，这样多进程能共享。

第三步，**并发与扩展**。单机先用内存版 MessageBus 跑通；要横向扩展就换 Redis 版 MessageBus + 起 multiple worker 进程，因为会话状态在 Redis，worker 之间无状态、可任意扩缩。Agent 内部工具调用还能按 `is_concurrency_safe` 分 sequential/concurrent 两批，安全工具并发跑省时间。

第四步，别忘了**治理**叠上去：限流（pre_execute hook + Token/QPS 级）、熔断（BudgetGate 超预算即停）、降级（模型 fallback）、审计（post_response 落库）。这些是「能跑」和「能上线」的差距。

这套东西 agentscope 框架只给了 building blocks（reply_stream、SessionService、MessageBus），产品级的 Runtime、Envelope、治理层是要自己加的——QwenPaw 就是个完整范本，它的 8 阶段 Runtime + Envelope SSE 状态机就是这套工业化的教科书实现。

> **要点速记**：① reply_stream 包成 SSE 长连接 + 心跳；② 加 Envelope 状态机把碎事件翻成带 seq 可恢复的标准消息；③ Runtime 阶段化，新功能挂 hook；④ SessionService 管会话状态机，存 Redis；⑤ 换 Redis MessageBus + 多 worker 横向扩展；⑥ 治理（限流/熔断/降级/审计）是能跑→能上线的差距。
>
> **源码佐证**：SSE 端点 `app/_router/_session.py`；SessionService `app/_service/_session.py`；MessageBus `app/message_bus/`；产品级 Runtime/Envelope 参考 QwenPaw `runtime/runtime.py`/`envelope.py`。
>
> **压轴一句话**：reply_stream→SSE 长连接，中间加 Envelope 翻译+Runtime 阶段化，SessionService 管 Redis 状态，换 Redis 总线多 worker 扩展，治理层决定能不能上线——框架给块，产品加层。
