## Q1：怎么治理 Agent 的死循环、超预算、无效迭代？（JD：Agent Loop 治理、解决断连/无效循环/执行失控）

### 【模范回答】

这道题是 JD 的核心痛点。业余做法是靠 `max_iters` 兜底——粗暴，治标不治本，超了就硬停，Agent 留下半拉子结果。专业做法叫 **Loop Engineering**，核心思想是：**把「该不该停」抽象成可插拔的 Stop Gate（停止门控），每种失控形态一个 gate，精准治理**。

真实失控不止「死循环」一种，我按 QwenPaw 的五个 gate 来讲，每个治一种病：

1. **DoomLoopGate**——治「反复调同一工具不收敛」。模型陷入怪圈反复 `ls`、反复 `search`。gate 检测连续同名工具调用超阈值就停。
2. **BudgetGate**——治「超预算」。一轮或累计 token 超阈值就熔断，防账单打爆。
3. **IterationGate**——治「超迭代次数」。比 max_iters 更细，可以按任务复杂度配。
4. **FileLoopGate**——治「文件循环」。反复读写同一文件，常见于改文件改不好来回折腾。
5. **StandaloneRubricGate**——治「评分不达标」。定义一个完成判据（如"回答必须含引用"），不达标继续迭代，达标才停——治「永远达不到完成标准」。

机制上，所有 gate 继承 `StopGate` 抽象基类，每轮推理前过一遍所有 gate，**任一触发就停**。gate 接入点是 Agent 的 `_reasoning`（QwenPaw 在这里挂 gate runner）。

这套设计的精妙在「可插拔」——**新增一种治理规则 = 加一个 gate，不改 Agent 核心**。而且每个 gate 独立可测、可独立开关。比「一个 max_iters 管所有」精准太多了：死循环有 DoomLoop、烧钱有 Budget、改文件改不好有 FileLoop、达不到标准有 Rubric，每种病一服药。

**断连**的治理单独说——靠**状态持久化 + 阶段化 resume**。Agent 状态 `state_dict` 序列化存盘，进程挂了能恢复；产品层 Runtime 把请求拆成 8 阶段，每阶段是 checkpoint，断连后按阶段续，比「全跑完才存」粒度细。SSE 层 Envelope 打 seq 序号支持断线重连续传。

所以「Agent Loop 治理」面试回答的关键是：**不要只说 max_iters**——要说多 gate 精准治理（doom/budget/iteration/file/rubric），可插拔、每种病一服药，加断连靠持久化+阶段resume。这是业余和专业的分水岭。

> **要点速记**：① 业余靠 max_iters 粗暴，专业用 Loop Engineering 多 gate 精准治理；② 五 gate：DoomLoop(反复调同工具)/Budget(超预算)/Iteration(超迭代)/FileLoop(文件循环)/Rubric(评分不达标)；③ 机制：继承 StopGate，每轮过所有 gate 任一触发即停，可插拔不改核心；④ 断连靠 state_dict 持久化 + Runtime 阶段 checkpoint resume + SSE seq 续传；⑤ 精髓：每种病一服药，加规则=加 gate。
>
> **源码佐证**：`StopGate` 基类（QwenPaw `loop/gates/base.py:61`）；五 gate（`doom_loop.py:43`/`budget.py:27`/`iteration.py:27`/`file_loop_gate.py:41`/`rubric.py:154`）；接入点 `agents/react_agent.py:366`（`_reasoning`）；runner/handler（`loop/gates/runner.py`）。
>
> **压轴一句话**：Loop Engineering 把停止条件做成可插拔 gate——doom/budget/iteration/file/rubric 各治一种失控，每轮过所有 gate 任一触发即停，比 max_iters 精准，断连靠持久化+阶段resume，加治理=加 gate 不改核心。

## Q2：怎么做 Agent 级流量治理？限流、熔断、降级、队列怎么落地？（JD：限流降级、Token/QPS级限流、队列缓冲）

### 【模范回答】

Agent 的流量治理和传统 Web 服务有区别——除了 QPS，还要管 Token（一个慢 Agent 占用时间长+烧 token 多），维度更多。我按四个手段讲。

**限流**。两个维度：**QPS 级**——按 Agent/租户/接口限制并发请求数，防止瞬时洪峰打垮；**Token 级**——按租户/Agent 限制单位时间 token 消耗，防止一个复杂 Agent 烧爆。落地点在 Runtime 的 `pre_execute` 阶段 hook——请求执行前过限流中间件，超限直接拒（429）或排队。QwenPaw `app/` 层有限流。

**熔断**。当某个 Agent/模型/工具持续失败或超预算，触发熔断，短时间内直接拒绝该路径请求，不再消耗资源，给后端喘息。比如 `BudgetGate` 超预算即熔断该 Agent；模型连续失败触发模型层熔断。熔断要配「半开」恢复机制——过一会试探性放一个请求，成功了再恢复。

**降级**。主路径不可用时切备选。模型层：`ModelConfig.max_retries` 重试可重试异常，全失败切 `fallback_model`——比如 qwen-plus 挂了降级到 qwen-turbo，保证服务不中断。功能层：RAG 检索挂了降级成「不检索直接答」并提示用户；沙箱不可用降级成只读模式。降级是保命的，宁可功能打折也不能整体不可用。

**队列缓冲**。长任务（多 Agent 协作、深度研究）不能让用户在 HTTP 连接上干等，要异步化——请求进队列，立即返回 task_id，后台 worker 消费，前端轮询或 WebSocket 拿结果。QwenPaw 的 `app/crons/`（APcheduler）+ task tracker 就是这套：长任务入队、状态机流转（pending/running/done/failed）、前端查状态。队列还能削峰填谷——突发流量进队列慢慢消化，不直接打垮 worker。Redis 做队列+状态存储。

这套组合的生产形态：请求进来先限流（QPS+Token 双维度），通过的进执行；执行中 BudgetGate 熔断、模型 fallback 降级；长任务进队列异步化；全程 Runtime 阶段 hook 可插拔治理。**灰度/A-B** 也是流量治理一部分——按 tenant/agent 路由不同配置（不同模型、不同 prompt、不同 gate 阈值），小流量验证再全量。这就对应 JD「灰度发布、A/B 测试」。

> **要点速记**：① 限流双维度：QPS级(防洪峰)+Token级(防烧钱)，挂 pre_execute hook；② 熔断：持续失败/超预算短路该路径，配半开恢复；③ 降级：模型 fallback_model + 功能降级(RAG挂不检索)，保命优先；④ 队列缓冲：长任务异步化入队+状态机+前端轮询，削峰填谷；⑤ 灰度A-B 按 tenant 路由不同配置。
>
> **源码佐证**：限流 QwenPaw `app/` 限流中间件 + Runtime pre_execute hook（`runtime/runtime.py:110`）；模型降级 `ModelConfig.max_retries/fallback_model`（`agent/_config.py:164`）；熔断 `BudgetGate`（`loop/gates/budget.py:27`）；队列 `app/crons/` + task tracker；Redis 存储 `app/storage/_redis_storage.py`。
>
> **压轴一句话**：Agent 流量治理四手段——限流(QPS+Token双维度挂pre_execute)、熔断(超预算/连续失败短路+半开恢复)、降级(fallback_model+功能降级保命)、队列缓冲(长任务异步化+状态机+削峰)，再加灰度A-B按租户路由——比传统Web多一个Token维度。

## Q3：怎么部署 Agent 服务？多活/容灾怎么考虑？（JD：容器化、CI/CD、高可用）

### 【模范回答】

部署这条线我从开发到生产讲。

**容器化**：用 Docker 多阶段构建——builder 阶段装依赖、runtime 阶段只拷产物，镜像小、启动快。固定 `agentscope==2.0.4` 避免版本漂移。DASHSCOPE_API_KEY 等密钥运行时注入（`docker run -e`），不进镜像。QwenPaw 的 `deploy/Dockerfile` 就是范本。

**编排**：K8s。app 容器无状态（会话状态在 Redis），可任意扩缩；Deployment + HPA 按 QPS/CPU 自动扩缩容；worker 进程多副本分担长任务。依赖的 Redis、Qdrant(向量库)用 StatefulSet 或托管服务。

**高可用/多活/容灾**关键在「**状态外置 + 无状态计算 + 降级**」三件事：
1. **状态外置**——会话状态、消息总线、队列都放 Redis（持久化+主从），app 进程无状态。任何一个 app pod 挂了，请求路由到别的 pod，从 Redis 继续状态，不丢会话。
2. **无状态计算扩缩**——app 无状态才能 HPA 弹性扩缩、滚动更新零停机。
3. **降级保命**——前面说的 fallback_model、功能降级，某依赖挂了服务还能用（打折）。
多活可以多 region 部署，Redis 跨 region 同步或各自 region 独立+流量按地域路由。容灾靠 Redis 持久化（AOF/RDB）+ 定期备份 + 跨可用区部署。

**CI/CD**：每个 PR 跑 pytest（QwenPaw `.github/workflows/` 有约 20 个 workflow），含单元/契约/集成/E2E（p0/p1/p2/slow 分级 + Playwright E2E），加 pre-commit lint。镜像构建推 registry，部署走 ArgoCD/Flux 自动同步。关键要有可观测（前面卡08）让你知道部署后有没有回归。

**安全**部署要点：密钥用 K8s Secret/外部密钥管理不进镜像和代码；沙箱后端按安全等级选（生产用 bubblewrap/独立容器）；审计落库；网络策略限制 Agent 出网（防数据外泄）。

我毕业项目做了 Docker 化 + 一个 SSE 服务入口（`app.py`），README 写清架构和运行。完整的 K8s 编排/多活是下一步，但 Docker + 无状态 app + Redis 状态外置这套基础是齐的，往生产推就是加 K8s 编排和托管中间件。

> **要点速记**：① 容器化：Docker多阶段构建，固定版本，密钥运行时注入不进镜像；② 编排：K8s，app无状态可HPA扩缩，Redis/Qdrant用StatefulSet或托管；③ 高可用三件事：状态外置(Redis持久化+主从)+无状态计算(零停机滚动更新)+降级保命；④ 多活多region+Redis同步/地域路由，容灾靠持久化+跨AZ；⑤ CI/CD：pytest(分级)+E2E+lint，镜像推registry自动部署，可观测防回归；⑥ 安全：密钥用Secret、出网限制、审计落库。
>
> **源码佐证**：Docker 范本 QwenPaw `deploy/Dockerfile`；CI QwenPaw `.github/workflows/`（~20个）；测试分级 `tests/`（unit/contract/integration/e2e + p0/p1/p2/slow）+ `e2e/`(Playwright)；状态外置 Redis `app/storage/_redis_storage.py` + `app/message_bus/_redis_message_bus.py`；我毕设 `code/w12/Dockerfile` + `app.py`。
>
> **压轴一句话**：部署=容器化(多阶段+密钥注入)+K8s编排(app无状态HPA扩缩)，高可用靠状态外置(Redis)+无状态计算+降级三件套，多活跨region，CI/CD跑分层测试+E2E防回归，安全管密钥和出网——Docker+无状态app+Redis状态外置是基础，往上加K8s和托管中间件即生产。
