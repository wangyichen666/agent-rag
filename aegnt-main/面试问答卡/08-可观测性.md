# 面试问答卡 08 · 可观测性（Trace / Token / 审计）

> 覆盖：W7 / W10。对应 JD：Trace 链路追踪、Token 消耗监控、执行耗时分析、调用审计、异常告警。

---

## Q1：怎么追踪一次 Agent 回复的完整链路？怎么监控 Token 防烧钱？

### 【模范回答】

可观测性是生产 Agent 的硬需求——出了问题你得能查「这次回复调了几次模型、几次工具、各花了多少 token、卡在哪」。agentscope 和 QwenPaw 分几层解决。

**链路追踪（Trace）**。一次用户提问到最终回复，内部可能经历「Leader→多次模型调用→多次工具调用→可能再 spawn Worker」，这是一棵调用树。框架提供 `TracingMiddleware`，基于 OpenTelemetry，产出三类 span——agent span（一次 Agent 回复）、llm span（一次模型调用，含模型名/token/耗时）、tool span（一次工具调用，含工具名/参数/结果/状态）。属性都定义在 `_tracing/_attributes.py`。你可以用 OTLP exporter 导出到 Jaeger/Tempo 这类后端可视化。挂上这个中间件，一次回复就变成可可视的 span 树，哪步慢、哪步失败一目了然。

**Token 监控**。每个模型调用都会在 `Msg.usage` 里带 `input_tokens`/`output_tokens`。但光有单条不够，要聚合。QwenPaw 做了完整体系：`TokenRecordingModelWrapper` 包装模型，每次 `__call__` 记录 token；`TokenUsageManager` 聚合统计，可以按 Agent、按轮次、按租户汇总；`turn_usage.py` 算单轮用量；`storage.py` 持久化。这样你能看到「这个 Agent 今天烧了多少」「这次复杂任务哪轮 token 最多」。

**防烧钱**靠 token 监控 + 预算门控联动。框架侧有 `ReplyBudgetControlMiddleware` 控回复预算；产品侧有 `BudgetGate`——设个阈值，累计 token 超了就熔断这一轮，不再增长。我毕业项目就挂了 BudgetGate，设 4000 token（教学调小），超了就注入停止指令 + max_iters 兜底。生产里按 Agent/租户设不同预算，防止一个失控 Agent 把账单打爆。

这套组合——Trace 看链路、Token 监控看消耗、Budget gate 兜底熔断——就是「Agent 上线后你睡得着觉」的基础。没有这些，一个 Agent 偷偷跑上百轮你都不知道。

> **要点速记**：① Trace：TracingMiddleware(基于OTel)产 agent/llm/tool 三类span，导到Jaeger看调用树；② Token：Msg.usage 带单条用量，TokenRecordingModelWrapper 包装记录，TokenUsageManager 聚合按Agent/轮次/租户；③ 防烧钱：ReplyBudgetControlMiddleware + BudgetGate 超预算熔断；④ 组合=Trace看链路+Token看消耗+Gate兜底。
>
> **源码佐证**：`TracingMiddleware`（`middleware/_tracing/_trace.py:116`）+ `_attributes.py`；`Usage`（`message/_base.py:57`）/`Msg.usage`（:84）；`ReplyBudgetControlMiddleware`（`middleware/_budget.py:21`）；产品级 `TokenRecordingModelWrapper`（QwenPaw `token_usage/model_wrapper.py:15`）+ `TokenUsageManager`（`:65`）+ `BudgetGate`（`loop/gates/budget.py:27`）。
>
> **压轴一句话**：TracingMiddleware 出 agent/llm/tool 三类 span 看链路，Msg.usage+TokenRecordingModelWrapper+TokenUsageManager 看消耗，BudgetGate 超预算熔断兜底——Trace+Token+Gate 三件套让你睡得着觉。

## Q2：调用审计记什么？怎么做异常告警？框架和产品的可观测性差别？

### 【模范回答】

**审计**和 Trace/Token 不一样，它偏**合规与追溯**——出了事要能查到「谁、什么时候、调了什么工具、传了什么参数、成功没、结果是什么」。这对企业 Agent 是硬合规要求，尤其工具调用涉及敏感数据或写操作时。

审计要记的字段：调用方身份（哪个 token / 哪个 Agent / 哪个租户）、时间戳、工具名、入参、执行结果摘要、成功/失败状态。要**落库**（不是只 print 日志），可追溯、可检索。QwenPaw 的 MCP 管理面 `app/routers/mcp.py` 把这些做成了策略/白名单/审计的管理 API；我自己毕设的 MCP Server 也让每次工具调用都走一个 `_audit` 函数记录「ts/tool/args/ok/结果长度」。要注意 stdio MCP Server 的审计不能 print 到 stdout（被协议占用），要走 stderr 或文件。

**异常告警**建立在可观测数据之上。几个抓手：Trace 捕获异常 span（标红失败节点）；Token/耗时设阈值，单次或累计超阈值触发告警（接钉钉/Slack/邮件）；工具执行失败率监控，某个工具连续失败触发告警；Budget 熔断事件本身也是一种告警信号。生产里通常接一个告警平台，把 Trace + Token + 审计的指标做规则，比如「单 Agent 5 分钟 token 过万」「工具失败率>30%」「Budget 熔断」都推告警。

**框架和产品的可观测性差别**，正好是边界。框架给的是**基础积木**：`TracingMiddleware`（OTel 打点）、`Msg.usage`（单条 token）、`ReplyBudgetControlMiddleware`（预算控制）——这些够你"能看到"。但产品级要的是**完整体系**：QwenPaw 加了 Langfuse 集成（`observability/langfuse.py`，偏产品侧的 trace/metrics 可视化看板，比纯 OTel 更面向运营）、完整的 `token_usage/` 监控体系（录制/聚合/存储/按租户）、审计管理面。框架给 OTel 基础，产品加 Langfuse 看板 + 完整监控 + 审计落库——又是那个「框架给块、产品加层」的模式。

所以做可观测性，不能只挂个 TracingMiddleware 就说"做了"——要 Trace + Token + 审计 + 告警四件套齐，且审计要落库、告警要触发，这套才是生产级。

> **要点速记**：① 审计记：谁/何时/调什么/参数/结果/成功否，落库(不只print)供合规追溯；② stdio MCP 审计走 stderr(stdout被协议占)；③ 异常告警：Trace异常span + Token/耗时阈值 + 工具失败率 + Budget熔断，接告警平台；④ 框架给基础(TracingMiddleware/Msg.usage/预算中间件)，产品加完整体系(Langfuse看板/token_usage聚合/审计管理面)。
>
> **源码佐证**：审计 MCP 管理面 QwenPaw `app/routers/mcp.py`；框架 `TracingMiddleware`（`middleware/_tracing/_trace.py:116`）；产品 Langfuse（`observability/langfuse.py`）+ `token_usage/`（manager:65/wrapper:15/storage）。
>
> **压轴一句话**：Trace+Token+审计+告警四件套才是生产可观测——审计记谁调了什么落库供追溯，告警靠阈值/失败率/熔断触发；框架只给OTel基础，产品加Langfuse看板+token聚合+审计管理面，又是框架给块产品加层。
