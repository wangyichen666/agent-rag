# 02 RAG 核心功能详解

> 本文档是整个系统最重要的设计文档，覆盖 Python AI 层（agent-rag-python）的全部核心链路：
> **离线索引**（文档 → 向量）与**在线问答**（问题 → 带引用的流式回答）。
> 每一节都给出：目标、方案对比、推荐默认参数、实现要点与坑。

## 0. 全景：两条链路

```
离线索引（文档入库，异步，分钟级）
  上传文档 → 解析清洗 → 智能切分 → Embedding → 写入向量库

在线问答（用户提问，实时，秒级）
  用户提问 → Query 改写 → 混合检索（稠密 + 稀疏/BM25）
          → Rerank 精排 → Prompt 组装 → LLM 流式生成（带引用）
```

设计原则：

1. **检索质量决定上限，生成只负责表达**——把精力优先放在解析、切分、检索、Rerank 上
2. **每一环都可观测**：记录每次问答的 query、召回 chunk、rerank 分数、最终上下文
3. **每一环都可替换**：解析器、切分器、向量库、LLM 全部接口化

## 1. 文档接入与解析

### 1.1 格式支持矩阵

| 格式 | 解析器 | 优先级 | 说明 |
|---|---|---|---|
| PDF（文字版） | PyMuPDF | P0 | 速度快，提取文本+页码+位置 |
| PDF（复杂版式/论文/双栏） | MinerU | P1 | 版面分析 + 阅读顺序还原，质量远高于直接抽文本 |
| PDF（扫描件） | MinerU + PaddleOCR | P1 | OCR 兜底 |
| Word（docx） | python-docx | P0 | 按标题层级提取，保留大纲结构 |
| Markdown / TXT | 直接读取 | P0 | 按标题切分最自然 |
| Excel（xlsx） | openpyxl → 转 Markdown 表格 | P2 | 按 sheet 处理 |
| PPT（pptx） | python-pptx | P2 | 按页提取 |
| 网页 HTML | BeautifulSoup / trafilatura | P2 | 去导航、广告 |

### 1.2 PDF 解析是质量分水岭

PDF 没有「段落」概念，只有字符坐标。直接抽文本会遇到：

- **双栏论文**：左右栏文字交错 → 需要版面分析（layout analysis）还原阅读顺序
- **表格**：抽出来是一堆散字 → 需要表格结构识别，转成 Markdown 表格再入库
- **页眉页脚/页码**：每页重复出现，污染语料 → 解析时按位置规则剔除
- **图片中的文字**：扫描件 → OCR

**推荐两级策略**：

```
快速通道：PyMuPDF 抽取 → 启发式清洗（去页眉页脚、连字符断行修复）
质量通道：MinerU（版式分析 + 表格公式识别 + OCR），产出结构化 Markdown
```

一期先上快速通道，接口预留 `parser: "fast" | "quality"`，二期接入 MinerU。

### 1.3 文本清洗规则（必做）

- 去除页眉页脚（按 y 坐标 + 重复模式检测）
- 修复断行：中文场景「行尾非标点则直接拼接」，英文场景处理连字符 `-`
- 规范化空白：连续空行 → 单个换行；全角/半角统一
- 去除乱码与控制字符
- 文档级去重：相同文件（hash）重复上传时拒绝或创建新版本

## 2. 切分（Chunking）

切分是 RAG 里**对效果影响最大、最容易被低估**的环节。

### 2.1 核心权衡

- chunk 太大：包含噪声、稀释语义、占上下文 token
- chunk 太小：语义不完整（「该方案分三步」但三步在另一个 chunk）
- 目标：**一个 chunk 表达一个完整语义单元**

### 2.2 切分策略对比

| 策略 | 做法 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| 固定长度 | 每 N token 一刀切 | 简单 | 切断句子语义 | 不用 |
| **递归字符切分** | 按 `["\n\n", "\n", "。", "；", " "]` 优先级递归切，直到 ≤ 限制 | 尊重自然边界，通用 | 不理解文档结构 | **默认兜底** |
| **结构感知切分** | 按 Markdown/Word 标题层级切，标题路径写入 metadata | 语义单元完整 | 依赖解析质量 | **首选**（docx/md/MinerU 产出） |
| 语义切分 | 相邻句子 embedding 距离突变处断开 | 语义最连贯 | 计算贵、不稳定 | 二期可选 |
| 父子分块 | 见 2.4 | 精度与上下文兼得 | 实现稍复杂 | **推荐二期默认** |

### 2.3 推荐默认参数

```yaml
chunk:
  chunk_size: 512        # token 数，中文知识库 400~600 是甜区
  chunk_overlap: 64      # 重叠 10%~15%，缓解边界切断
  min_chunk_size: 50     # 过短碎块并入相邻块
  separators: ["\n## ", "\n### ", "\n\n", "\n", "。", "；", "，"]
```

- Embedding 模型是 BGE-M3（上限 8192 token），512 远未触顶，瓶颈在「语义纯度」而非模型
- **重叠区在生成答案时可保留**，检索时重叠提高边界命中率

### 2.4 父子分块（Small-to-Big，强烈推荐）

```
父块（parent）：1024~2048 token，提供完整上下文 → 喂给 LLM
子块（child）：128~256 token，语义精确        → 参与向量检索
```

流程：子块做 embedding 入库（带 `parent_id`）→ 检索命中子块 → 取回其父块 → 父块进入 Prompt。
收益：检索精度由小块保证，答案完整性由大块保证。

### 2.5 特殊内容处理

| 内容 | 策略 |
|---|---|
| 表格 | 不拆行！整表转 Markdown 表格作为独立 chunk；超长表按「表头 + 若干行」复制表头分块 |
| 代码块 | 按函数/类边界切，不切语句中间 |
| 图片 | OCR 文字入 chunk；图注关联；一期可跳过纯图 |
| 标题 | 每个 chunk 的 metadata 记录标题路径（如 `["第3章", "3.2 架构"]`），切分时可把标题路径 prepend 到 chunk 文本前再 embedding（显著提升检索相关性） |

### 2.6 Chunk Metadata 规范（入库必带）

```json
{
  "doc_id": "d_123",
  "kb_id": "kb_01",
  "chunk_index": 17,
  "parent_id": "p_5",
  "title_path": ["第三章 系统设计", "3.2 总体架构"],
  "page": 42,
  "source_file": "系统设计说明书.pdf",
  "content_type": "text | table | code",
  "created_at": "2026-07-26T10:00:00"
}
```

metadata 的两个核心用途：**引用溯源**（答案展示出处页码）和**检索过滤**（知识库隔离）。

## 3. 向量化（Embedding）

### 3.1 模型选型

| 模型 | 维度 | 中文能力 | 特点 | 结论 |
|---|---|---|---|---|
| **BGE-M3** | 1024 | ★★★★★ | 单模型产出稠密+稀疏+多向量；8192 上下文；多语言 | **默认** |
| text-embedding-3-large | 3072 | ★★★☆ | 云端 API，免运维 | 数据可出网时备选 |
| GTE-Qwen2-7B-instruct | 3584 | ★★★★★ | MTEB 高分，但 7B 推理贵 | 效果追求极致且 GPU 充足时 |
| m3e | 768 | ★★★☆ | 轻量老牌 | 不推荐新项目用 |

### 3.2 BGE-M3 的三种输出（混合检索的基础）

1. **dense**：1024 维稠密向量 → 语义相似度
2. **sparse**：类 BM25 的词项权重（学习型稀疏向量）→ 关键词精确匹配
3. **multi-vector（ColBERT 风格）**：token 级交互，效果最好但存储/计算贵 → 一期不用

一期：dense 入库 + sparse 用于混合检索（等价于内置 BM25）。

### 3.3 推理部署要点

- **query 与 passage 非对称**：BGE 系列建议 query 侧加指令前缀（如 `"为这个句子生成表示以用于检索相关文章："`），passage 侧不加——细节以模型卡为准，封装在 embedder 内，调用方无感
- **批处理**：入库按 batch_size=32~64 推理；在线 query 单条推理
- **GPU 需求**：BGE-M3 约 2GB 显存即可流畅跑，CPU 也能跑（入库慢 10~20 倍，在线 query 单条约 50~100ms 可接受）
- **吞吐估算**：T4 单卡入库约 2000~5000 chunk/分钟
- **embedding 缓存**：按 `hash(model + text)` 缓存，避免重复计算（重复入库、相似 query）

### 3.4 向量归一化与度量

- 输出做 L2 归一化 → 内积（IP）等价于余弦相似度
- Milvus 建索引时 `metric_type="IP"`（归一化后）或 `"COSINE"`（2.4+ 直接支持）

## 4. 向量索引与存储

### 4.1 索引算法

| 算法 | 特点 | 结论 |
|---|---|---|
| **HNSW** | 图索引，召回率高、查询快，内存占用大 | **默认** |
| IVF_FLAT / IVF_PQ | 倒排聚类，内存省，召回略降 | 千万级以上再考虑 |
| FLAT | 暴力 | 仅调试 |

HNSW 关键参数（Milvus）：

```python
index_params = {
    "M": 16,               # 每节点边数，越大越准越耗内存（8~64）
    "efConstruction": 200, # 建索引质量（100~500）
}
search_params = {"ef": 64} # 查询时搜索宽度，越大越准越慢（≥ top_k）
```

### 4.2 Collection 设计（Milvus）

```python
fields = [
    FieldSchema("id", DataType.INT64, is_primary=True, auto_id=True),
    FieldSchema("kb_id", DataType.VARCHAR, max_length=64),      # 分区键
    FieldSchema("doc_id", DataType.VARCHAR, max_length=64),
    FieldSchema("chunk_id", DataType.VARCHAR, max_length=64),
    FieldSchema("parent_id", DataType.VARCHAR, max_length=64),  # 父子分块
    FieldSchema("content", DataType.VARCHAR, max_length=8192),  # 原文
    FieldSchema("metadata", DataType.JSON),                     # 见 2.6
    FieldSchema("dense", DataType.FLOAT_VECTOR, dim=1024),
    FieldSchema("sparse", DataType.SPARSE_FLOAT_VECTOR),        # BGE-M3 稀疏
]
```

- **分区策略**：按 `kb_id` 做 Partition Key，知识库间物理隔离，检索天然带过滤，删库即删分区
- **稀疏向量索引**：`SPARSE_INVERTED_INDEX`，度量 `IP`
- 标量字段 `kb_id/doc_id` 建索引加速过滤

### 4.3 数据一致性

- 文档删除 → 按 `doc_id` 表达式删除（`doc_id == "d_123"`）
- 文档更新 → 先删旧 chunk 再入库新版本；`kb_document` 表记录 `version`
- 重建索引：支持按知识库整体重建（解析/切分策略升级后重刷）

## 5. 在线检索（Retrieval）

### 5.1 Query 理解与改写

用户真实 query 常常**不适合直接检索**，改写是第一道质量杠杆：

| 技术 | 解决什么 | 示例 | 一期？ |
|---|---|---|---|
| **指代消解/多轮改写** | 多轮对话中「它」「这个方案」指代不明 | 「它的部署成本呢」→「vLLM 方案的部署成本呢」 | ✅ 必做 |
| **Query 扩展** | 短 query 信息量少 | 同义词/上下位词补充 | 可选 |
| **HyDE** | query 与文档文体不匹配 | 让 LLM 先写一段「假设答案」，用假设答案去检索 | 二期 |
| **子查询分解** | 复杂多跳问题 | 「对比 A 和 B 的延迟」→ 拆成 A 延迟、B 延迟两个子查询分别检索 | 二期 |

一期实现：多轮改写。用 LLM 以「历史 + 当前问题 → 独立完整问题」的固定 prompt 改写，便宜模型即可（如 DeepSeek），延迟 +200~400ms。

### 5.2 混合检索（Hybrid Search）

纯向量检索的盲区：**专有名词、型号、编号、缩写**（语义相近但字面必须精确，如「SN-7000 交换机」）。必须叠加关键词检索。

```
稠密检索：BGE-M3 dense → Milvus HNSW，top 20
稀疏检索：BGE-M3 sparse（或 ES/Milvus BM25），top 20
融合：RRF（Reciprocal Rank Fusion）
```

**RRF 公式**（对两路结果按排名融合，无需对齐分数量纲）：

```
score(d) = Σ  1 / (k + rank_i(d))     k 通常取 60
```

Milvus 2.4+ 支持多向量一次 hybrid search 并内置 RRF/加权融合；自研融合也就 20 行代码。

### 5.3 元数据过滤（权限与多知识库）

- 检索时强制过滤 `kb_id in [用户有权的知识库列表]`——**权限在检索层落实，不在生成后补救**
- 可选过滤：按文档类型、时间范围（如「只看今年的制度」）

### 5.4 召回数量与阈值

```yaml
retrieve:
  dense_top_k: 20
  sparse_top_k: 20
  rrf_k: 60
  rerank_top_n: 5        # 精排后留给 Prompt 的条数（3~6 是甜区）
  score_threshold: 0.35  # rerank 归一化分数阈值，低于则判为「无相关内容」
```

原则：**检索宁多勿漏（召回），Rerank 宁缺勿滥（精度）**。

## 6. Rerank 精排

### 6.1 为什么必须 Rerank

- 向量检索是**双塔**：query 和文档分别编码，交互浅，速度快但精度有限
- Reranker 是**交叉编码器（cross-encoder）**：query + 候选 chunk 拼接后联合编码，逐对打分，精度高但慢——所以只对 top 20~50 做精排

### 6.2 bge-reranker-v2-m3 使用要点

- 输入：`[query, passage]` 对，输出相关性分数（logits，可 sigmoid 归一化到 0~1）
- 长度：query + passage 拼接后截断到 512~1024 token（长 chunk 截断会损失信息——这也是 chunk 不宜过大的原因之一）
- 性能：T4 单卡对 20 个候选约 50~150ms，可接受
- 与 embedding 模型同族（都出自 BAAI），中英文混排稳定

### 6.3 阈值与降级

- 归一化分数 < 阈值（默认 0.35，需按评测集调）：判定「知识库无相关内容」→ 走拒答逻辑，**不硬答**
- Rerank 服务故障 → 降级为直接用 RRF 融合分数取 top 5，保证可用性（记日志告警）

## 7. Prompt 组装

### 7.1 上下文组装规则

1. **去重**：父子分块场景，多个子块命中同一父块时合并
2. **排序**：按 rerank 分数降序；有研究建议把最相关的放在开头和结尾（LLM「中间遗忘」现象）
3. **编号**：每段上下文编号 `[1] [2] [3]`，与引用系统联动
4. **token 预算**：

```
总预算 = 模型上下文 × 安全系数(0.8)
  - system prompt      ~300 token
  - 多轮历史           ~1000 token（超出则截断/摘要）
  - 检索上下文         ~2000 token（5 段 × 400）
  - 当前问题           ~100 token
  - 输出预留           ~1000 token
```

超长时按分数从低到高丢弃检索段落。

### 7.2 推荐 System Prompt 骨架

```
你是一个严谨的企业知识库助手。基于「参考资料」回答用户问题。

要求：
1. 只依据参考资料回答，资料中没有的内容，明确说"根据现有资料无法回答"，
   不要编造。
2. 回答中引用资料时，在对应语句末尾标注引用编号，格式 [1] [2]。
3. 回答使用简体中文，结构清晰，必要时使用列表。
4. 不要复述参考资料全文，用自己的话归纳。

【参考资料】
[1]（来源：系统设计说明书.pdf 第42页 · 3.2 总体架构）
{chunk_1}
[2]（来源：...）
{chunk_2}
...
```

### 7.3 拒答策略（防幻觉的最后防线）

- 触发条件：rerank 分数全部低于阈值
- 行为：不调 LLM 或调 LLM 但 prompt 不含资料，直接返回固定话术 + 「换个问法/联系管理员补充文档」建议
- 前端展示区分「有引用回答」与「拒答」

## 8. 生成与流式输出

### 8.1 LLM 调用参数

```yaml
llm:
  model: deepseek-chat        # 或本地 vLLM 的 Qwen2.5-14B-Instruct
  temperature: 0.1            # 知识库问答要低随机性
  max_tokens: 1024
  stream: true
```

### 8.2 流式协议（SSE）

Python → Java → 前端全链路 SSE，事件类型自定义（详见 03 文档）：

```
event: meta       data: {"session_id":"s_1","citations":[...]}   # 首包：引用元信息
event: token      data: {"delta":"根据"}                          # 逐 token
event: token      data: {"delta":"资料"}
event: done       data: {"usage":{...},"latency_ms":1830}
event: error      data: {"code":"LLM_TIMEOUT","message":"..."}
```

要点：

- **引用信息先发（meta）**，前端可立即渲染引用面板，答案流式填充
- Java 层只透传不解析 token，仅在 `done` 时落库完整消息
- 断连处理：前端断开后 Java 取消下游请求，避免 Python 空跑烧 token

### 8.3 多轮对话

- 历史窗口：保留最近 5~10 轮，按 token 截断（从最早开始丢）
- 历史压缩（可选）：超长会话用 LLM 生成滚动摘要替换旧轮次
- 多轮检索：见 5.1 指代消解，改写后的独立 query 才进检索
- 落库：每轮 QA 连同 citations、检索中间结果一起存（评测与审计的原料）

## 9. 高级扩展（二期/三期储备）

| 特性 | 说明 | 价值 |
|---|---|---|
| 查询路由 | 多知识库时先判「该问哪个库」 | 多库场景准确率 |
| Agentic RAG | 检索不到 → 自动改写重检/换库/联网，多步决策 | 复杂问题 |
| GraphRAG | 实体关系抽取建图谱，应对跨文档总结类问题 | 全局问答（「今年所有项目风险汇总」） |
| Auto-merging | 相邻子块命中多则自动合并父块 | 上下文完整性 |
| 假设性问题索引 | 为每个 chunk 预生成「它能回答的问题」并入库 | 提升召回 |
| 表格问答 | 表格 chunk 走 Text2SQL/代码解释器 | 结构化数据 |

一期坚决不做，但接口与数据模型预留空间。

## 10. 质量评估（必须尽早建立）

没有评测集的 RAG 调优是盲人摸象。**第一周就开始攒评测集**。

### 10.1 评测集构建

- 从真实用户问题/业务方访谈收集 50~200 条「问题 → 应命中的文档段落 → 参考答案」
- 也可用 LLM 对现有文档自动生成问题，人工抽检

### 10.2 检索层指标（不依赖 LLM，可自动化）

| 指标 | 含义 | 目标 |
|---|---|---|
| Recall@k | 正确段落是否进入 top k（k=20） | ≥ 90% |
| Hit Rate@5 | top5 命中率（rerank 后） | ≥ 85% |
| MRR | 首个正确结果排名的倒数均值 | 越高越好 |
| nDCG | 考虑排序位置的加权指标 | 越高越好 |

### 10.3 生成层指标（RAGAS 框架）

- **Faithfulness（忠实度）**：答案是否忠于检索到的资料（防幻觉核心指标）
- **Answer Relevancy**：答案与问题的相关度
- **Context Precision/Recall**：上下文质量回测检索层

### 10.4 调优飞轮

```
线上问答落库 → 抽样人工标注 bad case → 归因（解析？切分？检索？生成？）
→ 针对性调整（参数/策略）→ 评测集回归 → 上线
```

常见归因速查：

| 症状 | 大概率病因 |
|---|---|
| 答案说「资料没有」但明明有 | 检索没召回 → 查切分粒度、混合检索、top_k |
| 召回了但答案没用上 | Rerank 排错 / Prompt 组装丢段 |
| 答案张冠李戴 | chunk 太大混入噪声 / 上下文排序问题 |
| 表格问题答非所问 | 表格被拆碎 → 表格整块入库 + 表头复制 |
| 多轮追问翻车 | 缺指代消解改写 |

## 11. 性能与稳定性工程

### 11.1 延迟预算（在线问答，目标 TTFT < 2s）

| 环节 | 预算 | 手段 |
|---|---|---|
| Query 改写 | 300ms | 用便宜快模型；可关闭（首轮无历史时跳过） |
| 混合检索 | 100ms | Milvus 本地网络；ef 不宜过大 |
| Rerank（20 条） | 150ms | GPU；候选数控制 |
| LLM 首 token | 1000ms | 取决于模型；上下文别太臃肿 |
| 合计 TTFT | ~1.6s | 各环节并行优化空间：改写与 embedding 并行 |

### 11.2 缓存

- **Embedding 缓存**：hash(text+model) → 向量，Redis/本地
- **检索缓存**：相同（kb_id + query 改写结果）短 TTL 缓存
- **答案缓存**：谨慎——知识更新后失效问题，建议只缓存检索不缓存最终答案

### 11.3 并发与限流

- Python 层：FastAPI 全异步；Embedding/Rerank 为 GPU 阻塞调用，放独立线程池/进程池（`run_in_executor`），避免阻塞事件循环
- 按用户/租户限流（Java 层做，如每用户 10 QPS）
- 入库任务：队列化 + 并发上限（防止批量上传把 GPU 打满影响在线）

### 11.4 降级策略

| 故障 | 降级 |
|---|---|
| Rerank 不可用 | RRF 分数直取 top5，告警 |
| 稀疏检索不可用 | 退化为纯稠密检索 |
| LLM 超时 | SSE error 事件 + 可重试；已生成部分保留 |
| 向量库不可用 | 明确报错「服务维护中」，不编造 |
