# 05 部署与开发路线图

## 1. 部署架构（Docker Compose 起步）

```yaml
# docker-compose.yml 服务清单（示意，非完整可运行版）
services:
  mysql:          # 业务库
    image: mysql:8.0
  minio:          # 文档对象存储
    image: minio/minio
  etcd:           # Milvus 依赖
    image: quay.io/coreos/etcd:v3.5.5
  milvus:         # 向量库（standalone 模式起步）
    image: milvusdb/milvus:v2.4.x
    depends_on: [etcd, minio]
  agent-rag-python:      # FastAPI，GPU 副本单独标注 deploy.resources
    build: ../agent-rag-python
    environment:
      - VECTOR_STORE=milvus
      - EMBEDDING_MODEL=bge-m3
      - LLM_BASE_URL=https://api.deepseek.com   # 或内网 vLLM 地址
      - LLM_API_KEY=${LLM_API_KEY}
  agent-rag-java:        # Spring Boot
    build: ../agent-rag-java
    environment:
      - AI_BASE_URL=http://agent-rag-python:8000
      - AI_INTERNAL_TOKEN=${AI_INTERNAL_TOKEN}
  agent-rag-front:       # Nginx 托管静态产物 + 反向代理 /api
    build: ../agent-rag-front
    ports: ["80:80"]
```

演进路径：单机 Compose（POC）→ 双机分离（GPU 机跑 Python 模型副本）→ K8s（生产多副本 + 弹性伸缩）。

## 2. 硬件与环境需求

| 组件 | 最低（POC） | 推荐（生产） |
|---|---|---|
| MySQL + MinIO + Milvus | 4C8G | 8C16G，SSD |
| Python（Embedding+Rerank，GPU） | T4 16G 或 RTX 3060 12G | T4/A10；CPU 模式仅够 demo |
| Python（本地 LLM，可选） | — | Qwen2.5-7B-int4：≈8GB；14B-int4：≈12GB；建议 24G 卡（如 4090/A10） |
| Java | 2C4G | 4C8G |

> 若 LLM 走云端 API，一块 T4 即可覆盖 Embedding + Rerank，全系统门槛很低。

## 3. 开发里程碑

### M1：最小闭环（第 1~2 周）

目标：一个用户、一个知识库、PDF 上传、流式问答跑通。

- [ ] 三个仓库脚手架（Vite / Spring Initializr / FastAPI 骨架）
- [ ] Python：PyMuPDF 解析 → 递归切分 → BGE-M3（CPU 亦可）→ Milvus 入库
- [ ] Python：`/v1/chat/completions`（稠密检索 top20 直取 top5，无 rerank）+ SSE
- [ ] Java：登录 JWT、知识库/文档 CRUD、MinIO 上传、ingest 同步调用、SSE 透传
- [ ] 前端：登录页、知识库管理页、对话页（流式渲染 + 引用展示）

验收：上传一份 PDF，提问得到带引用的流式回答。

### M2：检索质量（第 3~4 周）

- [ ] 混合检索（dense + sparse RRF 融合）
- [ ] bge-reranker-v2-m3 精排 + 阈值拒答
- [ ] 结构感知切分（标题路径 metadata + prepend）
- [ ] Query 改写（多轮指代消解）
- [ ] 召回测试页 + 50 条评测集 + Recall@20 基线

验收：评测集 Recall@20 ≥ 90%，bad case 有归因记录。

### M3：生产化（第 5~6 周）

- [ ] 知识库级权限 + 检索层过滤
- [ ] 消息反馈（赞/踩）、检索 debug 落库、Langfuse 接入（可选）
- [ ] 异步任务队列化（文档入库）、限流、降级开关
- [ ] MinerU 质量通道（复杂 PDF）、父子分块
- [ ] Docker Compose 一键部署 + 监控告警

验收：多用户多知识库权限隔离；连续一周线上 bad case 率可统计、可回归。

### 后续储备（按需）

- Agentic RAG（检索不到自动改写重检）、GraphRAG（跨文档总结）、表格问答（Text2SQL）

## 4. 风险与对策

| 风险 | 等级 | 对策 |
|---|---|---|
| PDF 解析质量差（表格/双栏/扫描件） | 高 | 快速通道兜底 + MinerU 质量通道；bad case 归因制度 |
| 中文切分破坏语义 | 中 | 结构感知切分 + 标题 prepend + 重叠；评测集回归 |
| 答案幻觉 | 高 | rerank 阈值拒答 + 低 temperature + 强制引用 + Faithfulness 评测 |
| GPU 成本/资源不足 | 中 | LLM 走云端 API；Embedding/Rerank 单 T4 即可；CPU 兜底 demo |
| Java/Python 契约漂移 | 中 | Python OpenAPI 为准生成 Java 客户端；契约测试进 CI |
| 多轮对话指代错误 | 中 | 改写 prompt 持续迭代；rewritten_query 落库可查 |

## 5. 团队协作建议

- **契约先行**：03 文档评审通过后，Python 先提供 mock server（FastAPI 自带假数据），Java/前端并行开发
- **评测先行**：M1 期间同步攒评测集，不要等 M2
- **每周 bad case 评审**：AI 层 + 业务方一起看真实问答记录，决定调优优先级
